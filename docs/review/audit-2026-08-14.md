## Findings

### M1 — `matchPersisted` walks an unsorted buffer against sorted refs
**Claim.** `matchPersisted` does one monotonic forward walk over `batch`, matching each
`model.EventRef` in order. That is correct only if `batch` is in non-decreasing TS order; it never
is (it is the worker's arrival-order accumulation buffer), while `WriteBatch` returns refs sorted by
(TS, Seq). Most events are never published, and an equal-TS event can be paired with another event's
ref, publishing a wrong `Seq`.
**Evidence.** pipeline.go:626-636 (`i` never reset, `break` on exhaustion) fed from
pipeline.go:471/500 with `buf` accumulated at pipeline.go:381; write.go:73-80 sorts a copy by
(TS, DedupKey) and write.go:201-210 sorts the refs again by (TS, Seq). With
`buf = [e1(10:00:05), e2(10:00:01)]`, e1 is never published. The doc at pipeline.go:612-614 asserts
the opposite of what `WriteBatch` does. The only test (pipeline_test.go:396-417) uses a fake writer
returning refs in input order with distinct increasing TS.
**Fix.** Key the mapping on identity that survives the write: have `WriteBatch` return
`(DedupKey, TS, Seq)` triples and index `batch` by `DedupKey` in `matchPersisted`.
**Scope.** `pipeline.go`, `store/postgres/write.go`, `store/store.go` (`EventRef` gains `DedupKey`),
plus a pipeline test with an out-of-order buffer and duplicate TS. ~1/2 day.

### M2 — abandoned-session sweep job is never scheduled
**Claim.** SPEC §2.4/§3.8 make the periodic sweep the only producer of `status='abandoned'`.
`Serve` starts partitions, rollups and retention — there is no sweep job anywhere.
**Evidence.** serve.go:105/113/123; jobs.go defines no `SweepJob`; app.go:56-59 has no sweep field.
`SweepAbandoned` (store.go:84, pool.go:156) has zero non-test callers; `ARGUS_SWEEP_INTERVAL` /
`ARGUS_SESSION_IDLE_TIMEOUT` (config.go:63-64) are read nowhere. upsert_session.go:456 only
*preserves* an existing `abandoned`. SPEC.md:952/1286 require it; no PLAN ticket, no ledger row.
`sim` generates 15 % abandoned sessions, so the Phase-4 demo will show them all active.
**Fix.** Add `SweepJob` to jobs.go shaped like `RollupJob` (ticker + `TryLock`), calling
`SweepAbandoned(ctx, cfg.SessionIdleTimeout)` on `cfg.SweepInterval`; construct in `New`, start in
`Serve`.
**Scope.** `jobs.go`, `app.go`, `serve.go` + an app-level test through `New`+`Serve` asserting an
idle session flips. ~2 h.

### M3 — `sessions.entrypoint` can never be populated
**Claim.** The projection looks up the attribute `entrypoint`; Claude Code emits `app.entrypoint`
(`resource.app.entrypoint` after §3.4 prefixing). The column is permanently NULL while the read API
and OpenAPI example advertise a value.
**Evidence.** upsert_session.go:229-231 vs the adjacent, correct `app.version` /
`resource.service.version` block at :224-228. Wire name confirmed at
docs/research/telemetry-surfaces.md:44 and SPEC.md:137. No producer of a bare `entrypoint` attribute
exists in the repo (incl. `sim`), so no fixture can catch it; read_sessions.go:239 and openapi.yaml
still expose it.
**Fix.** Read `app.entrypoint` with a `resource.app.entrypoint` fallback; emit the attribute from
`internal/sim`'s identity set.
**Scope.** `upsert_session.go`, `internal/sim` identity attrs, one projection test. ~1 h.

### M4 — `ARGUS_SHUTDOWN_GRACE` is spent twice
*(merges the concurrency and ops-deploy reports of the same root cause)*
**Claim.** One context with the full grace is passed to both `http.Server.Shutdown` and the ingest
drain. If in-flight requests consume the grace, `Pipeline.Close` takes its `ctx.Done()` branch,
cancels workers, and every queued/buffered batch is dropped with Postgres healthy — and the process
exits non-zero.
**Evidence.** serve.go:142-147 (single `shutdownCtx`, 15 s default at config.go:39). Nothing bounds
request duration: only `ReadHeaderTimeout` is set (serve.go:86-89) and chi's `Timeout` is 30 s
(router.go:23) — larger than the grace. pipeline.go:319-341 -> `p.cancel()` -> in-flight
`WriteBatch` returns `context.Canceled` -> `ClassTransient` (retry.go:96-98) -> drop
(pipeline.go:588-593).
**Fix.** Give each step its own budget: keep `shutdownCtx` for `Shutdown`, derive a fresh `drainCtx`
(or split the grace explicitly) for `drainIngest`.
**Scope.** `serve.go` (+ the doc comment at :160-166), one test with a handler that outlives the
grace. ~1 h.

### M5 — one NUL / NaN destroys the whole accumulated batch
**Claim.** Nothing sanitises vendor strings or float attrs. A `\x00` in any string attr makes the
`attrs` jsonb cast fail (SQLSTATE 22P05, classed permanent); a NaN/+-Inf OTLP DoubleValue makes
`json.Marshal` fail (classed transient). Either way the error covers the entire `WriteBatch`, so up
to `ARGUS_INGEST_BATCH_SIZE` (500) events from unrelated sessions and requests are dropped, with a
2xx already returned to every client.
**Evidence.** normalize/otlpattrs.go:36-42 and hooks.go:98 pass values verbatim; events.go:127
marshals, :210 binds `$36::jsonb[]`. Verified: 22P05 on the jsonb cast, `unsupported value: NaN` on
marshal; retry.go:75 prefixes -> permanent, non-PgError -> transient; both reach
`pipeline.go:471-476 p.dropEvents(batch, ...)` over the whole buffer. No sanitisation anywhere
(`ToValidUTF8|u0000|IsNaN|IsInf` -> no hits). The "fail-safe" fallbacks at otel_logs.go:175-185 are
dead — the same map is re-marshalled in the store. Reachable from ordinary traffic (tool I/O over a
file containing a NUL, with `OTEL_LOG_TOOL_DETAILS=1`).
**Fix.** Sanitise once in `normalize`, where all sources converge: strip/replace `\x00` in decoded
strings, drop or stringify non-finite float64s.
**Scope.** `normalize/otlpattrs.go`, `normalize/hooks.go` + round-trip tests for a NUL attr and a
NaN doubleValue. ~3 h. (Per-event isolation on permanent write errors is a separate, larger ticket.)

### M6 — ingest writes have no deadline and no lock timeout
**Claim.** Every `WriteBatch`/`WriteMetrics` runs on `p.ctx` (plain `WithCancel(Background)`), with
no per-attempt timeout and no `statement_timeout`/`lock_timeout` on the pool. A statement blocked on
a lock — e.g. behind `RetentionJob`'s in-process `DROP TABLE <events partition>`, which needs ACCESS
EXCLUSIVE on the parent and itself queues behind any long analytics read — parks a worker
indefinitely; retry classification never runs because the call never returns. With `Workers=4`, four
stalls take the event lane offline.
**Evidence.** pipeline.go:222, pipeline.go:551 (`write(p.ctx)`), no `WithTimeout` in flushEvents
(:471-473) / flushMetrics (:514-516). `NewPool` sets only MaxConns, exec mode, application_name;
`statement_timeout|lock_timeout` matches nothing in server/ or deploy/. jobs.go `RetentionJob.tick`
-> retention.go:101-132 drops all expired partitions in one transaction. No HTTP handler timeout
either, so the blocking reader is itself unbounded.
**Fix.** Wrap each attempt: `attemptCtx, cancel := context.WithTimeout(p.ctx, writeTimeout)` inside
`retryLoop` (DeadlineExceeded is already classed transient), and set
`RuntimeParams["lock_timeout"]` in `NewPool`.
**Scope.** `pipeline.go` (attempt timeout + new config key) and `store/postgres/pool.go`
(RuntimeParams) — two files, two owners; sequence or coordinate. ~3 h.

### M7 — shutdown drain coalesces the backlog into one unbounded write
**Claim.** The `stopCh` drain loop appends every remaining batch into one buffer and flushes once,
with no `BatchSize` check. With `QueueCap=1024` batches, one worker can build a single transaction of
hundreds of thousands of events; if it fails or overruns the deadline the *entire* backlog is lost,
where steady state would have lost only the last partial batch.
**Evidence.** pipeline.go:388-402 vs the steady-state guard at :383-386; `runMetricWorker` repeats it
at :436-445. Defaults QueueCap 1024 / BatchSize 500 (pipeline.go:66-77). `WriteBatch`
(write.go:68-98) does no chunking — one Begin/Commit — and the whole thing runs through the retry
loop (RetryConflict=8).
**Fix.** Add `if len(buf) >= p.cfg.BatchSize { flush() }` inside both drain loops.
**Scope.** `pipeline.go`, plus a Close test with a backlog > BatchSize. ~1 h.

### M8 — rollup `date_trunc` runs in session TimeZone, Go keys are UTC
**Claim.** Every rollup statement derives its bucket key with `date_trunc(...)` (evaluated in the
connection's TimeZone GUC) while Go builds bucket keys — and the read API's query keys — in hard UTC.
Nothing pins TimeZone. On a non-UTC database the daily pass matches zero rows *after* having DELETEd
the day's rows, so `rollup_daily` stays permanently empty and every window > 7 days reads zeros;
half-hour-offset zones break the hourly pass the same way.
**Evidence.** rollups.sql:199 (and :103, :146/:153, :221) vs dirty.go:31-34, rollups.go:188-197,
read_analytics.go:172-178 (all `time.UTC`). pool.go:69-92 sets only `application_name`; no
`AfterConnect`, no `ALTER DATABASE ... SET timezone`. Reproduced on postgres:18-alpine:
`SET TIME ZONE 'Europe/Paris'` + the real Delete/Insert pair with the Go day key -> `INSERT 0 0`;
`Asia/Kolkata` `date_trunc('hour','...10:20Z')` -> 09:30Z.
**Fix.** `cfg.ConnConfig.RuntimeParams["TimeZone"] = "UTC"` in `NewPool`, and defensively write
`date_trunc('hour', ts, 'UTC')` in rollups.sql. Add a test against a pool with TimeZone
`Europe/Paris`.
**Scope.** `pool.go`, `db/queries/rollups.sql` + sqlc regen, one rollup test. ~3 h.

### M9 — rollup aggregates cannot prune partitions or use an index
**Claim.** `AggregateEventRollup`, `AggregateToolCallRollup` and `FetchMetricRowsForRollup` filter
only on `date_trunc('hour', <col>) = ANY($buckets)`. `date_trunc(text, timestamptz)` is STABLE and
pruning applies to the partition key, not an expression over it, so recomputing one dirty hour
sequentially scans every retained `events` and `metric_samples` partition — once per 60 s tick.
**Evidence.** rollups.sql:103/:153/:221; no expression index exists in migrations or partitions.go.
Verified on postgres:18-alpine (6 partitions, 60 000 events, ANALYZEd): `Append -> Seq Scan` on all
six, no `Subplans Removed`; adding a plain range bound yields `Subplans Removed: 5`. Fires every tick
because `runRollupsLocked` always injects curHour/prevHour.
**Fix.** Add a sargable range predicate built from the claimed bucket set:
`AND e.ts >= $from_ts AND e.ts < $to_ts` (min bucket, max bucket + 1 hour / 1 day).
**Scope.** `db/queries/rollups.sql` + sqlc regen + `rollups.go` arg plumbing; an EXPLAIN assertion in
the store tests. ~4 h. Same file as M8 — one ticket.

### M10 — `scripts/smoke.sh` destroys the live stack's volume
**Claim.** smoke.sh runs `docker compose -f deploy/docker-compose.yml down -v` on entry and in its
EXIT trap, on the same compose file (hence same project name and same `argus-pgdata` volume) that
`make compose-up` and the README quickstart use. Running the documented `make compose-smoke` on a
host with a live Argus stack silently deletes that stack's database.
**Evidence.** smoke.sh:15/:25/:30 — no `-p`, no `COMPOSE_PROJECT_NAME` anywhere in the script or
Makefile; project name derives from the `deploy` directory. deploy/docker-compose.yml:48-49 declares
the persistent volume; Makefile:71-72 uses the identical `-f`. README.md advertises both targets side
by side with no warning.
**Fix.** `COMPOSE_PROJECT_NAME=argus-smoke` (or `-p argus-smoke` on every call) in smoke.sh.
**Scope.** `scripts/smoke.sh` one-liner. ~15 min.

### M11 — no `ReadTimeout`/`WriteTimeout`/`IdleTimeout`
**Claim.** Only `ReadHeaderTimeout` is set. chi's `Timeout` only cancels the request context — it
does not interrupt `io.ReadAll(r.Body)` — so a client that finishes headers and trickles the body
holds a connection and goroutine indefinitely, on endpoints unauthenticated by default.
**Evidence.** serve.go:86-89 is the whole server config. `chimw.Timeout(30s)` at router.go:157 wraps
only the context; neither hooks/handler.go:168 nor otlp/codec.go:126 observes `r.Context()`.
`ARGUS_INGEST_TOKEN` defaults empty (config.go:49) and `requireBearerToken` returns `next` unwrapped
on an empty token (middleware.go:65-67); default bind is `:8080`.
**Fix.** Set `ReadTimeout`/`WriteTimeout` (~30 s, aligned with `requestTimeout`) and `IdleTimeout`
(~60 s) on the `http.Server`.
**Scope.** `serve.go` one-liner. ~30 min.

### M12 — `rebuild-projections --from-ts` TRUNCATEs everything
**Claim.** The fresh path unconditionally `TRUNCATE`s sessions/turns/tool_calls/subagents, then
replays only events >= `fromTS`. So `--from-ts=X` permanently destroys every projection row older
than X, with no warning, dry-run or confirmation — and any session whose raw events retention already
dropped loses its projection rows entirely.
**Evidence.** rebuild.go:163, rebuild.go:220-230; fetchEventPage (:126-131) reads only `events`,
whose old partitions retention.go:127-131 dropped. main.go:303 documents `--from-ts` as merely a
starting point. rebuild_test.go only asserts the resume path does not re-truncate. (The
retention-vs-rebuild tension is spec-level — SPEC.md:948 scopes "never deleted" to *raw retention* —
the defect here is truncate scope != replay scope.)
**Fix.** Scope the truncation to the replay range (`DELETE FROM sessions WHERE last_event_at >=
fromTS`, cascading), refuse a `fromTS` older than the oldest surviving events partition without an
explicit force flag, and print the row counts about to be destroyed.
**Scope.** `rebuild.go` (+ a force flag in `cmd/argusd/main.go`), one test for the scoped delete.
~4 h.

### M13 — `rebuild-projections` takes no lock against live ingest
**Claim.** `replayPage` re-runs the same *additive* projection upserts `WriteBatch` uses, and nothing
serialises a rebuild against a running `serve`. Any event ingested after the TRUNCATE and before the
cursor passes it is counted twice, silently inflating `event_count`, token totals and `cost_usd` —
defeating the "rebuild produces identical rows" guarantee (SPEC §1.6).
**Evidence.** rebuild.go:174-209 acquires no lock; upsert_session.go:445 `event_count =
sessions.event_count + EXCLUDED.event_count` and :471-476 the additive token/cost sums. Contrast
migrate.go:38 (`pg_advisory_lock` ARGUS01) and rollups.go:52 (`pg_try_advisory_xact_lock` ARGUS02).
main.go:300-337 opens its own pool with no liveness check.
**Fix.** Take a session-scoped advisory lock (ARGUS03) for the whole rebuild and have the ingest
write path take it in shared mode; minimally, refuse the subcommand when another argusd is connected
and document that the server must be stopped. Test: ingest during a rebuild, assert `event_count`
matches the event row count.
**Scope.** `rebuild.go` (+ shared-mode acquire in `write.go`), one integration test. ~4 h. Same file
as M12 — one ticket.

### M14 — tampered cursor -> 500 with internal error text
**Claim.** httpapi's cursor validation is strictly shallower than the store decoder's, so a cursor
valid at the HTTP layer but malformed at the store layer escapes the 400 path and surfaces as a 500
echoing store internals. SPEC §4.1 and `BadRequest.invalidCursor` require 400.
**Evidence.** cursor.go:101 accepts any payload with non-empty `k` and `len(Values) != 0` — no
arity/type check; params.go:171-174 passes the raw string through. postgres requires
`len(payload.V) == 2` (read_sessions.go:138) and unmarshals typed values (:153-181), wrapping
`postgres.ErrInvalidCursor` — a sentinel with no `errors.Is` anywhere in `query`/`httpapi`, so
sessions.go:86 writes 500 with `err.Error()`. `{"k":"last_event_at","v":["x"]}` reproduces it. Same
gap on /events, /sessions/{id}/timeline and both tool-call routes; /turns does it correctly
(sessions.go:244-256). Handler tests use the Fake, which does no cursor decoding.
**Fix.** Expose a `store.ErrInvalidCursor` sentinel on the seam (aliasing the postgres one) and map
it to `writeProblem(400, "invalid-cursor")` in every list handler's error path.
**Scope.** `store/store.go`, `store/postgres/read_*.go` (sentinel alias),
`httpapi/{sessions,events,toolcalls}.go`, handler tests exercising a malformed cursor. ~4 h.

### M15 — OpenAPI's `POST /ingest/hook` 202 contradicts the implementation
**Claim.** openapi.yaml declares the 202 body as `IngestAck` (`required: [status]`, enum
`[accepted]`); the handler returns `{"ok":true,"event":"<hook_event_name>"}`. The 413 and 429

worked in parallel with no merge conflict. Where a test file lives in the same package as the
production file it exercises, the test change belongs to the production ticket.

### Sequencing notes

- **Paired tickets:** M6 is split across two owners (per-attempt timeout in W1, `lock_timeout` in W3)
  and M12 across two (rebuild.go in W8, the `--force` flag in W9). Both pairs are additive and
  non-overlapping, but must land in the same wave or the fix ships half-done.
- **W6 must land with or after W7's response-shape decisions**, otherwise spec and code drift again.
- **W12's M16 fix should land before W3**, so the DataQuality assertions are real when the rollup
  changes land underneath them.
- **W5's `store.ErrInvalidCursor` alias** touches `read_sessions.go` / `read_events.go` /
  `read_toolcalls.go`, which no other Wave-1 ticket owns — keep it that way.
- **Highest urgency for Phase 4 specifically:** W1 (M1 breaks the SSE publish seam Phase 4 fills, and
  m7 fixes the contract its hub will rely on), W2 (M2 makes the Phase-4 session-status UI show wrong
  data), W4 (M3 makes a field the Phase-4 UI renders permanently NULL), W10 (M10 can delete a
  developer's demo database mid-phase).
